# 企业数字员工任务生命周期看板设计

## 目标

将任务页收敛为生产运营的受控执行入口。值班与运营人员能快速识别需要人工处理的数字员工任务，了解其生命周期状态，并在保留审计证据的前提下完成审批、接管、重试和归档。

本期只保留四个核心模块：

1. **任务处置**：识别并处置待处理、执行中、等待人工动作、风险异常和已完成任务。
2. **执行控制**：查看数字员工执行状态、关键步骤、失败原因，并暂停或重试。
3. **人工治理**：完成审批、人工接管、策略拦截和 SLA 升级。
4. **审计追溯**：回溯任务来源、关键操作、执行证据和最终结果。

本期不构建通用项目管理、协作或排期能力。

### 成功标准

- 值班人员在首屏 10 秒内识别需要自己处理的高风险或待审批任务。
- 所有改变任务状态的操作都能追溯到明确的操作者、原因、时间和结果。
- 页面只呈现支持“下一步行动”的信息；其他事实进入只读详情或审计。

## 页面结构

```text
任务控制台
├─ 行动摘要：待处理 / 待审批或接管 / 风险异常
├─ 工作工具栏：搜索、状态、负责人、风险、更多筛选、新建
├─ 生命周期主面板：看板 / 紧凑列表
└─ 右侧任务抽屉：概览、执行、人工治理、审计
```

| 核心模块 | 页面承载位置 | 用户问题 | 不承担的职责 |
| --- | --- | --- | --- |
| 任务处置 | 行动摘要、工具栏、看板/列表 | 哪些任务现在需要处理？ | 项目排期、协作分工 |
| 执行控制 | 抽屉“执行” | 数字员工进行到哪一步、能否暂停或重试？ | 编辑执行编排或资产 |
| 人工治理 | 抽屉“人工治理” | 是否需要审批、接管或升级？ | 配置长期审批策略 |
| 审计追溯 | 抽屉“审计” | 任务因何而起、谁做了什么、结果如何？ | 手工维护日志 |

### 生命周期

看板按以下五段固定排序：

```text
待处理 -> 执行中 -> 等待人工动作 -> 风险异常 -> 已完成
```

- 待处理：等待受理、分派或开始执行。
- 执行中：数字员工正在运行，显示当前步骤和进度。
- 等待人工动作：等待审批、双签或人工接管。
- 风险异常：执行失败、SLA 超时、依赖阻塞或策略拦截。
- 已完成：已完成、待确认归档的短期记录；归档内容通过筛选查看。

拖放是状态流转请求，不直接更新页面状态。Mock API 拒绝无效流转并返回业务原因。

#### 状态流转与守卫规则

| 当前阶段 | 允许下一阶段 | API 守卫 |
| --- | --- | --- |
| 待处理 | 执行中 | 已分派且具备执行权限 |
| 执行中 | 等待人工动作、风险异常、已完成 | 审批策略、执行结果与依赖均满足 |
| 等待人工动作 | 执行中、待处理 | 审批通过或人工接管完成 |
| 风险异常 | 执行中、等待人工动作 | 错误可重试，或已发起人工治理 |
| 已完成 | 已归档 | 用户确认且无未结治理项 |

已归档任务不出现在默认看板，只能通过“已归档”筛选以只读方式查看。依赖阻塞、策略拦截和无权限不会伪造状态流转；接口返回原因与建议动作，前端保留原任务状态。

### 行动摘要和工具栏

首屏仅保留三张可点击摘要：待处理、待审批或接管、风险异常。点击后复用风险/状态过滤条件，并显示当前过滤条件和“清除”入口。工具栏提供搜索任务标题、编号、来源，状态、负责人和风险筛选；不提供复杂标签和多维筛选。

不保留：任务模板、附件管理、评论协作、子任务、独立时间线、我的任务、复杂标签体系、批量编辑、批量改优先级、批量归档、非行动型 KPI、成功率、风险地图及面向项目排期的编辑功能。来源、资产与依赖不提供编辑能力，只读展示关联信息和阻塞提示。

### 任务卡和紧凑列表

任务卡展示：优先级与 SLA、标题、当前阶段和数字员工、负责人、风险/人工动作标记、来源。卡片点击打开详情抽屉；卡片不展示多个行内操作。超过 SLA、需签核、执行失败和阻塞必须具有文本标签，不能只依赖颜色表达。

紧凑列表列为：任务编号与标题、当前阶段、优先级、负责人、数字员工、SLA、最后更新。行内唯一操作是打开详情。

### 详情抽屉

抽屉是深度操作唯一入口，顶部展示标题、编号、优先级、阶段、SLA 和来源。

| 标签 | 内容 |
| --- | --- |
| 概览 | 目标、阶段、负责人、数字员工、SLA、来源与只读关联对象及阻塞提示 |
| 执行 | 当前步骤、关键工具调用、结果、失败原因、暂停与重试记录 |
| 人工治理 | 审批/双签、策略拦截、人工接管、升级记录与处置原因 |
| 审计 | 创建、流转、审批、接管、执行和完成的时间序列证据 |

抽屉底部按阶段只显示一个主操作：待处理为开始执行或分派；等待人工动作为批准、驳回或接管；风险异常为重试或接管；执行中为暂停；已完成为确认归档。若同一阶段存在多种治理动作，显示一个主按钮和一个“更多治理操作”菜单，避免并列主按钮。驳回、接管和归档要求输入原因并二次确认。

抽屉打开时请求任务详情与审计；关闭后保留看板位置。移动端抽屉全屏显示，桌面端宽度为 480–560px；ESC、遮罩点击和关闭按钮行为一致，提交中的不可逆操作不可通过意外关闭中断。

## 视觉与交互

- 浅色企业运营界面，保留现有全局主题变量。
- 靛蓝 `#4f46e5` 仅用于品牌、选中状态、链接和主操作。
- 红色用于超时、失败、阻塞、驳回；黄色用于临期和需关注；绿色用于成功与完成。
- 卡片白底、12px 圆角、细边框和轻微阴影；悬停仅提升边框和阴影。
- 页面标题 16px/600，区域标题 14px/600，任务标题 14-15px/500-600，正文 13px，辅助信息 11-12px，技术标识使用等宽字体。
- 所有写操作在请求期间禁用重复提交，并在操作位置显示 loading、成功或失败说明；遵循 `prefers-reduced-motion`。
- 默认看板在宽屏横向滚动但不压缩卡片；小于 1024px 时优先切换紧凑列表，或将看板单列横向滚动，不能隐藏阶段或 SLA。
- 键盘操作支持 Tab 焦点、Enter/Space 打开任务、ESC 关闭抽屉；所有图标按钮都有可访问名称。

## Mock API 与领域状态

任务的最终事实状态由 `packages/api/src/mock.ts` 的统一 Mock 领域状态维护。任务页只通过查询和 mutation 渲染、提交并刷新缓存，不再维护独立的任务事实副本。

接口与最小契约：

```text
GET  /api/tasks
POST /api/tasks
GET  /api/tasks/:id
POST /api/tasks/:id/transition
POST /api/tasks/:id/approve
POST /api/tasks/:id/takeover
POST /api/tasks/:id/retry
GET  /api/tasks/:id/audit
POST /api/mock/reset
```

`GET /api/tasks` 支持状态、负责人、风险、来源、审批状态和归档状态筛选；列表项包含看板渲染所需的阶段、优先级、SLA、负责人、数字员工、来源和风险摘要。`GET /api/tasks/:id` 返回执行、治理、只读关联和版本。每个写请求携带 `version`；接口返回更新后的任务、追加的审计事件与可选提示文案。

写接口校验生命周期、审批、依赖、策略、权限和版本冲突；返回更新后的任务与新增审计事件。业务失败使用可识别错误码：`E_APPROVAL_REQUIRED`、`E_DEPENDENCY_BLOCKED`、`E_POLICY_BLOCKED`、`E_FORBIDDEN`、`E_VERSION_CONFLICT`。前端将错误呈现在触发操作的位置，并对可恢复错误提供重试入口。

Mock 覆盖 80ms、800ms、3s 三档延迟，以及以下固定场景：P0 超时并需要升级、待双签、执行失败可重试、依赖阻塞不可完成、策略拦截需接管、版本冲突需刷新。`POST /api/mock/reset` 可恢复这些初始场景，便于演示与回归测试。

## 验收和验证

1. 首屏可识别待处理、待审批/接管与风险异常任务。
2. 看板和列表显示相同领域状态；点击任务始终打开右侧抽屉。
3. 创建、流转、审批、接管、暂停、重试和归档均经过 Mock API。
4. API 阻止无效操作并在当前操作处展示可理解的原因。
5. 页面不再出现通用项目管理功能。
6. 看板、列表、摘要与抽屉在 mutation 后展示同一份 Mock 领域状态和审计记录。
7. 窄屏、键盘导航与减少动态效果场景可用；风险状态不只通过颜色传达。
8. 执行 `pnpm --filter @de/web-api typecheck`、`pnpm --filter web typecheck`、`pnpm --filter web build` 与 `git diff --check`。
