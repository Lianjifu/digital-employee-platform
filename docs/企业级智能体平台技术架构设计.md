## 二、各层详细设计

### 1. 接入层（Access Layer）

**职责**：统一入口，完成协议转换、鉴权、限流、路由分发

| 组件 | 技术选型建议 | 说明 |
|---|---|---|
| API 网关 | Kong / APISIX / Spring Cloud Gateway | 统一入口，负责路由、限流、熔断、鉴权前置 |
| Web前端 | React + TypeScript + Vite | 会话、智能体编排画布等交互界面 |
| BFF层 | Node.js (NestJS) / Go (Gin) | 面向不同端（Web/Mobile/开放API）做接口聚合裁剪 |
| IM渠道适配器 | 独立微服务，按渠道协议（企业微信/飞书 OpenAPI、Webhook）做消息格式转换 | 对应"渠道中心"业务模块 |
| 长连接网关 | WebSocket / SSE网关（用于流式对话输出） | 支撑会话模块的流式响应体验 |

---

### 2. 应用与服务层（Application & Service Layer）

**职责**：承载各业务域的领域服务，与一级菜单模块一一对应，微服务化拆分

| 领域服务 | 对应业务模块 | 核心设计要点 |
|---|---|---|
| Session Service | 会话 | 会话状态管理、上下文窗口截断策略、流式响应 |
| Task Service | 任务 | 任务队列（生产者-消费者模型）、状态机管理、重试策略 |
| Agent Service | 智能体 | 智能体元数据管理、版本发布、灰度策略 |
| Workflow Service | 工作流 | 流程定义存储（DAG/JSON Schema）、流程实例管理 |
| Knowledge Service | 知识中心 | 文档处理流水线、RAG检索编排 |
| Skill Service | 技能中心 | Skill/MCP/Tool三类能力的注册与元数据管理 |
| Model Gateway Service | 模型中心 | 见"模型层"详述 |
| Channel Service | 渠道中心 | 渠道绑定关系、消息路由规则 |
| App Service | 应用中心 | 应用编排配置、低代码表单引擎 |
| Evaluation Service | 评测中心 | 测试集管理、评测任务调度 |
| Guardrail Service | 安全护栏中心 | 内容审核规则引擎 |
| Workspace/IAM Service | 工作区+设置 | 多租户、RBAC权限模型 |
| Developer Platform Service | 开发者中心 | API Key、Webhook管理 |

**设计原则**：
- 采用**领域驱动设计（DDD）**划分微服务边界，与业务模块一一对应，避免服务粒度过细导致的调用链膨胀
- 服务间通信：同步调用用 gRPC（内部）/ REST（对外），异步解耦用消息队列
- 每个服务独立数据库（Database per Service），避免跨服务直接读库

---

### 3. 编排与推理层（Orchestration & Reasoning Layer）

**职责**：平台的技术核心，负责将模型的"推理能力"转化为可执行的智能体行为

| 组件 | 核心能力 | 技术选型建议 |
|---|---|---|
| Agent Runtime | 实现 ReAct / Plan-and-Execute / Reflexion 等智能体推理范式，管理思考-行动-观察循环 | 可基于 LangGraph / 自研状态机引擎 |
| 工作流引擎 | DAG编排、条件分支、循环、并行节点调度 | Temporal / Airflow（偏批处理）/ 自研轻量引擎（偏实时） |
| Tool Calling适配器 | 统一不同模型厂商的 Function Calling 协议格式 | 自研适配层，屏蔽模型差异 |
| MCP Client/Server框架 | 标准化接入外部系统能力 | 基于官方 MCP SDK 自研 Server/Client 管理 |
| 记忆管理（Memory Manager） | 短期上下文管理（滑动窗口/摘要压缩）+ 长期记忆（用户画像、历史摘要存储） | 短期存Redis，长期存向量库+关系库 |
| Prompt编排引擎 | Prompt模板管理、变量注入、版本控制 | 自研模板引擎，支持Jinja2风格语法 |

**关键设计**：Agent Runtime 是区别于普通 RAG 系统的核心，需要支持**多步推理的中断恢复**（长任务场景下Agent执行到一半系统重启，状态不丢失），建议将Agent执行状态外部化存储（而非仅存于内存），配合任务模块实现异步长任务的可靠执行。

---

### 4. 模型层（Model Layer）

**职责**：屏蔽底层模型差异，提供统一、可治理的模型能力供给

| 组件 | 核心能力 | 技术选型建议 |
|---|---|---|
| 模型网关 | 统一API格式、多模型路由、负载均衡、失败自动降级（Fallback）、限流 | 自研网关 / LiteLLM / OneAPI |
| LLM推理服务 | 自研/开源模型的高性能推理部署 | vLLM / TGI / SGLang（自建）；直接对接闭源API（Anthropic/OpenAI等） |
| Embedding & Rerank服务 | 向量化、语义重排 | BGE系列 / 自建embedding服务 |
| 模型评测框架 | Benchmark跑分、灰度对比 | 对接评测中心 |

**关键设计**：模型网关需支持**多租户配额隔离**（不同工作区/智能体的Token用量独立计费）与**成本归因打点**（每次调用记录 workspace_id / agent_id，供观测中心做成本分析）。

---

### 5. 数据与存储层（Data Layer）

| 存储类型 | 技术选型建议 | 用途 |
|---|---|---|
| 向量数据库 | Milvus / Weaviate / PGVector（轻量场景） | 知识库语义检索、长期记忆存储 |
| 关系型数据库 | PostgreSQL（主推，支持JSON+向量插件） / MySQL | 业务元数据（智能体配置、工作流定义、用户权限等） |
| 对象存储 | S3 / MinIO / OSS | 文档原文件、模型文件、导出结果存储 |
| 缓存 | Redis | 会话上下文、热点数据、分布式锁 |
| 消息队列 | Kafka（高吞吐场景） / RocketMQ | 异步任务解耦、事件驱动架构 |
| 搜索引擎 | Elasticsearch | 全文检索、日志检索、混合检索（BM25+向量） |
| 时序数据库 | Prometheus / VictoriaMetrics | 监控指标存储 |
| 图数据库（可选） | Neo4j | 知识图谱场景，复杂关系推理 |

---

### 6. 基础设施层（Infra Layer）

| 组件 | 技术选型建议 | 说明 |
|---|---|---|
| 容器编排 | Kubernetes | 统一调度所有微服务与推理服务 |
| GPU资源池 | KubeRay / NVIDIA GPU Operator + 虚拟化（MIG/vGPU） | 提升GPU利用率，支持多模型共享资源池 |
| Service Mesh（可选） | Istio | 大规模微服务场景下的流量治理 |
| CI/CD | GitLab CI / ArgoCD（GitOps） | 智能体/工作流配置变更也纳入版本化发布流程 |
| 配置中心 | Nacos / Apollo | 动态配置热更新 |
| 日志采集 | Filebeat + Kafka + ELK | 统一日志管道 |

## 三、横切治理能力（贯穿全栈）

### 1. 安全护栏（对应"安全护栏中心"）
- 请求侧：在应用服务层入口做**Prompt注入检测**、**内容审核前置拦截**
- 响应侧：在模型网关出口做**输出内容过滤**、**敏感信息脱敏**
- 实现方式：独立的**规则引擎+分类模型**双通道，规则引擎处理确定性规则（敏感词），分类模型处理语义级风险（越狱意图识别）

### 2. 可观测性（对应"观测中心"）
- **Trace**：基于 OpenTelemetry 统一埋点标准，贯穿"接入层→应用服务→编排推理→模型层"全链路，每次Agent执行生成完整Span树
- **Metrics**：Prometheus采集各层QPS/延迟/错误率，Grafana可视化
- **Logs**：结构化日志统一采集，ELK检索
- **APM**：SkyWalking / Datadog 做调用链关联分析

### 3. 多租户隔离（对应"工作区"）
- **逻辑隔离（推荐默认）**：所有数据表带 `workspace_id` 字段，服务层强制注入租户上下文过滤
- **物理隔离（高安全场景）**：按工作区拆分独立的 K8s Namespace 甚至独立数据库实例
- 向量库、缓存Key均需带租户前缀，防止跨租户数据泄露

### 4. IAM权限与审计（对应"设置"）
- 统一身份认证：OAuth2 / OIDC，对接企业已有SSO
- 权限模型：RBAC（角色）+ ABAC（基于属性，如"仅本工作区可见"）结合
- 审计日志：所有敏感操作（智能体发布、权限变更、数据导出）强制记录不可篡改审计日志（可选区块链存证/WORM存储）

## 四、端到端请求链路示例（一次会话请求）

```
用户发消息
  → 接入层：网关鉴权 + 限流
  → Session Service：加载会话上下文
  → Guardrail Service：输入内容安全检测
  → Agent Runtime：加载智能体配置，启动推理循环
      → 判断是否需要检索知识 → 调用 Knowledge Service（RAG检索）
      → 判断是否需要调用工具 → 调用 Skill Service（Tool/MCP执行）
      → 调用 Model Gateway → 路由至具体LLM推理服务 → 流式返回Token
  → Guardrail Service：输出内容安全检测
  → Session Service：更新会话上下文，写入存储
  → 接入层：流式返回给前端
  
【全链路旁路】：Observability Service 异步采集每一跳的 Trace/Metrics/Log
```

## 五、部署架构建议

- **计算资源分池**：CPU密集型服务（业务服务层）与GPU密集型服务（模型推理）分别调度到不同节点池，避免资源争抢
- **推理服务弹性伸缩**：基于QPS/队列深度做 HPA（Horizontal Pod Autoscaler），结合预留实例应对突发流量
- **多活/灾备**：核心业务服务多可用区部署；模型推理服务可采用"本地推理+云端API降级"的混合部署，保障高可用
- **灰度发布**：智能体/工作流的版本发布通过流量染色实现灰度验证，与"智能体版本管理"模块联动

## 六、非功能性设计要点

| 维度 | 设计要点 |
|---|---|
| 高可用 | 关键服务无状态化，支持水平扩展；模型网关配置多供应商Fallback |
| 弹性扩缩容 | 业务服务基于K8s HPA；GPU推理服务基于队列深度动态扩容 |
| 多租户隔离 | 默认逻辑隔离，高安全客户可选物理隔离 |
| 安全合规 | 传输层TLS全加密，存储层KMS密钥管理，符合等保/GDPR等合规要求 |
| 成本可控 | 模型网关做Token用量精细化计量，支持按工作区预算告警熔断 |
| 可扩展性 | 技能中心的Tool/MCP采用标准协议接入，新增能力无需改动核心引擎代码 |
